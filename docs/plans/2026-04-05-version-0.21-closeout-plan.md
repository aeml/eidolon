# Eidolon 0.21 Closeout Plan

> For Hermes: finish 0.21 completely before broad 0.22 work. Use TDD for behavioral fixes and regression coverage. Keep changes incremental on `master`.

Goal: close the 0.21 release line by finishing the remaining reliability, performance, and QA hardening work that directly supports the already-shipped dungeon/game-feel/menu foundation.

Architecture: keep 0.21 focused on stability and polish, not feature sprawl. The remaining work falls into three tracks: instance-transition correctness, HUD update sanity, and reproducible QA tooling. Each track should ship in small vertical slices with regression tests and live verification.

Tech Stack: Vanilla JavaScript client, Three.js, Go authoritative server, MongoDB persistence, Jest, ESLint, Go test, browser QA.

---

## Why 0.21 is not done yet

What is already true:
- dungeon progression, room-state rewards, objective guidance, entrance hints, auto-loot, combat intent, UI extraction, menu polish, and game-feel work are already shipped in the 0.21 line
- the current player-facing version is `Alpha 0.21.4`
- the game feels better than it did, but there is still structural debt under the hood

What still blocks a real 0.21 closeout:
- instance transitions still rely on broad scene cleanup paths and ad hoc mesh removal in `GameEngine.enterInstance(...)`
- dynamic HUD surfaces likely still do too much update work when nothing changed
- QA still leans too hard on full live runs instead of a fast repro path

Bluntly: 0.21 already has enough features. What it needs now is to stop being fragile.

---

## 0.21 release gates

0.21 is done only when all of these are true:

### Gate 1 — Instance transition correctness
- scene groups are the canonical transition boundary
- instance entry/exit clears dynamic entity/effect state without nuking persistent environment state
- player mesh, lights, environment meshes, and dungeon/overworld rebuilds land in the correct groups
- regression tests prove instance transitions preserve persistent groups and clear only the right runtime content

### Gate 2 — HUD update sanity
- high-frequency UI paths stop doing unnecessary work every frame
- HUD/objective/buff/combat-intent surfaces update on diffed or throttled state
- no visible regressions in gameplay responsiveness
- tests cover the throttled/diffed behavior where practical

### Gate 3 — QA and repro hardening
- there is a practical repro/sandbox path for menu/combat/dungeon feel checks
- there is an updated manual QA checklist for the core 0.21 surfaces
- future polish slices can be verified without depending entirely on a full live session every time

### Gate 4 — Release validation
- targeted Jest coverage for changed systems passes
- full JS test suite passes
- lint passes
- `go test ./...` passes from `server/`
- targeted browser QA is completed for:
  - dungeon enter/exit
n  - menu/modal flows
  - combat-intent/loot/HUD surfaces touched by the closeout work

### Gate 5 — Release presentation
- final 0.21 patch notes entry is added above `0.21.4`
- older patch-note entries remain intact
- version text only rolls forward to 0.22 when 0.21 is actually closed

## Track A — Scene-group instance transition correctness

This is the first implementation slice. Do this before anything broader.

### Findings already confirmed
- `RenderSystem` already has:
  - `environmentGroup`
  - `entityGroup`
  - `effectGroup`
- `ChunkManager` already uses `renderSystem.entityGroup`
- `RenderSystem.add()` already routes meshes into `entityGroup`
- `RenderSystem.clearInstanceScene()` currently clears only entity/effect groups
- `GameEngine.enterInstance(...)` still contains extra ad hoc cleanup and scene-level assumptions around remote players and transition rebuilding

That means the foundation exists, but the transition contract is still not clean enough.

### Objective
Make instance transitions rely on explicit scene-group ownership instead of broad scene surgery or mixed assumptions.

### Files
- Modify: `src/core/GameEngine.js`
- Modify: `src/core/RenderSystem.js`
- Modify: `src/world/WorldGenerator.js`
- Test: `tests/GameEngineDungeonContainment.test.js`
- Test: `tests/GameEngineDungeonRoomState.test.js`
- Optional if needed: related tests covering transition cleanup or scene ownership

### Definition of done
- all dynamic entity cleanup uses render-system/group-aware removal paths
- instance transition code does not fall back to removing all scene children
- player mesh re-entry goes through the intended entity path
- environment rebuilds stay scoped to environment content
- tests prove persistent environment/light/group structure survives transitions

### Task A1 — Strengthen transition regression coverage
1. Extend `tests/GameEngineDungeonContainment.test.js`
2. Add assertions for:
   - remote player mesh cleanup not removing persistent groups
   - player mesh returning to `entityGroup`
   - `clearInstanceScene()` being the transition boundary rather than raw scene child loops
   - overworld return preserving lights/environment group attachment
3. Run targeted tests and confirm they fail before implementation if behavior is still too loose

### Task A2 — Clean `GameEngine.enterInstance(...)`
1. Remove broad scene-clearing fallback behavior from `enterInstance(...)`
2. Route dynamic cleanup through render-system and chunk-manager semantics
3. Keep environment cleanup/rebuild explicit and reversible
4. Avoid hidden side effects like directly stripping scene children when a group-aware path should exist

### Task A3 — Tighten render-system ownership helpers
1. Add any missing helper needed to reset only dynamic content or only environment content safely
2. Keep `RenderSystem` as the owner of scene-group boundaries
3. Make the cleanup semantics obvious at runtime

### Task A4 — Verify transition behavior
Run:
- `npm test -- --runTestsByPath tests/GameEngineDungeonContainment.test.js tests/GameEngineDungeonRoomState.test.js`
- `npm test -- --runInBand`
- `npm run lint`
- `(cd server && go test ./...)`

Commit target:
- `refactor: tighten instance transition scene ownership`

## Track B — HUD diffing and throttling

### Objective
Stop doing unnecessary HUD/UI work every frame while keeping the game responsive.

### Suspect surfaces
Start by auditing these before changing anything:
- health/mana/xp/stats displays
- objective panel / journal summary surfaces
- buff/debuff tracker
- combat-intent or target info surfaces
- any hotbar or timer surfaces that update continuously without state change

### Files
- Modify: `src/core/GameEngine.js`
- Modify: `src/ui/UIManager.js`
- Modify: extracted UI modules as needed
- Test: relevant HUD-focused tests under `tests/`

### Definition of done
- high-frequency UI uses cached state or throttled cadence where per-frame updates are unnecessary
- no flicker, stale state, or delayed updates that feel broken
- tests or targeted assertions protect the new update policy

### Task B1 — Audit high-frequency update paths
1. Identify exact update methods called every frame or near every frame
2. Rank them by obvious waste and user-facing risk
3. Pick the smallest high-value cluster first instead of trying to fix everything at once

### Task B2 — Add state diffing
1. Add minimal cached-state guards for unchanged HUD values
2. Keep logic dumb and readable
3. Do not introduce a fake framework or overbuilt state layer

### Task B3 — Add throttling where safe
1. Apply throttling only to surfaces that do not need per-frame precision
2. Prefer simple timestamps or last-render snapshots
3. Verify no noticeable lag in feedback

### Task B4 — Validate
Run targeted tests for affected surfaces, then full validation.

Commit target:
- `perf: throttle and diff high-frequency hud updates`
