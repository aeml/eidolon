## Implemented local recovery safety correction

Source inspection found that the legacy Mongo-only restore helper chose an
archive automatically, interpolated its basename into a container shell and
did not check whether the Compose API was still running. The helper now requires
an exact readable gzip archive and `--confirm-data-loss`, one running Mongo
container and a stopped, not-yet-started or absent Compose API. Running, paused, restarting,
unknown, ambiguous and failed state lookups refuse before restoration. It does
not stop services itself. The host `.env` is no longer executed as shell code.

Archive bytes stream on stdin with `--nsInclude=eidolon.*` and `--stopOnError`;
other databases and archive-name shell expansion are excluded. Partial-failure
warnings remain. A successful Mongo check leaves all writers stopped and does
not replace the required matching journal/server recovery plan. This is not a
global lock: operators must stop external writers and prevent concurrent deploys.
The operations README now documents the explicit confirmation and limitations.

`TestRestoreArchiveRequiresExplicitStoppedTarget` executes the real script
against fake Docker/Mongo commands in temporary directories:18 scenarios passed
in.507s. Cases cover refusal, hostile filename characters, unchanged stdin bytes,
container credentials, restore failure and post-restore verification failure.
An initial fake-command harness typo failed the four stream cases and was fixed;
no production behavior was weakened to pass. Bash syntax and whitespace pass.
This proves script guards/quoting, not an actual Mongo round trip or an approved
production recovery. No live credentials, Docker socket, database or service
was used. These changes remain local1.19 work, excluded from the1.18 candidate.
